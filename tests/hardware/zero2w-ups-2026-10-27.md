# Zero 2W: DFR0528 UPS and OS battery indication

Hardware: Orange Pi Zero 2W / H618, DFRobot DFR0528 on the standard 40-pin
connection. Image: Armbian 26.11.0-trunk.108 / Ubuntu 26.04; kernel
`6.18.57-current-sunxi64`. The USB modem was excluded from this investigation.

## Discovery and real telemetry

Initially `power_supply` was empty and only PMIC and HDMI-DDC adapters existed.
Physical header **3 = PI8/SDA**, **5 = PI7/SCL** were unclaimed. The stock
`sun50i-h616-i2c1-pi` overlay enables `/soc/i2c@5002400` on those pins. It was
combined offline with the existing `pwm1-pi11` overlay before enabling it.
After reboot this controller appeared as `/dev/i2c-2`; that number is not a
portable board constant. No scan of the PMIC or HDMI bus was performed.

Targeted byte reads at `0x10` returned:

| Register | Value | Meaning |
|---|---|---|
| `0x01` | `0xdf` | DFR0528 product ID |
| `0x02` | `0x13` | MCU firmware 1.3 |
| `0x03`, `0x04` | `0x0b`, `0x3b` | 3.59375 V |
| `0x05`, `0x06` | `0x33`, `0xd0` | 51.8125% |

This is the **DFRobot MCU protocol**, not direct MAX17043 registers. Read-only
driver sources, DKMS configuration, overlay, tests and installation/rollback
instructions are in [hardware/dfrobot-ups](../../hardware/dfrobot-ups/README.md).

## Kernel and UPower

The native AArch64 module built with matching headers and installed through DKMS.
Temporary registration of `dfr0528` at the verified controller/address produced
`/sys/class/power_supply/dfr0528-2-0010`. The initial driver sample was **36% /
3.55375 V**, later **35% / 3.53375 V**. It polls every five seconds. Three
unbind/rebind cycles passed and subsequent polling resumed.

UPower 1.91.1 automatically created
`/org/freedesktop/UPower/devices/battery_dfr0528_2_0010` with vendor DFRobot,
model DFR0528, correct voltage and integer percentage. Its aggregate
`DisplayDevice` also has that percentage and a battery level icon. No private
D-Bus service or fake sysfs device is used.

The custom `zero2w-dfr0528` overlay was added to `user_overlays`, retaining
`overlays=pwm1-pi11 i2c1-pi`. A second reboot changed the boot ID and the kernel
automatically loaded/bound the module to the DT child
`/soc/i2c@5002400/ups@10`. No `new_device` command was needed after boot.
Post-reboot Linux/UPower readings were **32% / 3.53375 V**, DKMS remained
installed, and the kernel log showed firmware 1.3 with no Oops/BUG/Call trace.
The operator confirmed the board was running **only from the battery** during
the test. Declining SOC therefore agrees with the reported supply arrangement.
The final reading was **31% / 3.53375 V**; LightDM and UPower were active, with
HDMI disconnected. This does not establish charger detection or switchover.

**Status limitation:** the MCU has no charging/external-power/current register.
The kernel and individual UPower battery correctly report `Unknown`. UPower
nevertheless infers `discharging` for DisplayDevice and `on-battery=yes` because
no mains supply is reported. This is a daemon heuristic, not a UPS measurement;
it can activate existing battery policies even with a charger connected. The
individual UPower battery uses a missing-battery icon for unknown status, while
DisplayDevice has a normal level icon. Zero Wh/W values in `upower -d` mean
unsupported data, not measured energy/current. Runtime is not available.

The existing UPower configuration was not changed: action threshold 2%, effective
critical action PowerOff on this image. Firmware 1.3 reportedly cuts output below
5% per the manufacturer. **The existing OS threshold therefore does not establish
orderly shutdown before the HAT cutoff.** No low-battery shutdown, charger
switchover, electrical load or capacity qualification is claimed here.

## Desktop configuration

The user's panel had no power plugin. With XFCE/xfconfd stopped, configuration
was backed up and a `power-manager-plugin` entry (ID 16) added to panel 1.
`xfce4-power-manager` property `/xfce4-power-manager/show-panel-label=1` selects
percentage in XFCE 4.20. Existing panel items and power policies were retained.
The user could not log in during this test; physical desktop observation remains
pending. Configuration alone is not evidence that the monitor displayed an icon.

## Matching header recovery

The APT index still referenced trunk.108, but beta mirrors had removed its
header package in favour of trunk.112. A mirror returning HTTP 200 served HTML;
SHA256 validation rejected that file before installation.

The original build artifact was retained at:

```text
ghcr.io/armbian/os/kernel-sunxi64-current:6.18.57-S2ff6-D68f5-P6641-C8cea-H0759-HK01ba-Vc222-Bc354-R448a
tar SHA256: de7ad922415ad44962ce94edc28c10e24ee7326cede6e2bb53f660ca516c79e1
headers deb SHA256: 187ee5a741f2277b67eb3a69be8e5fb149b30df1335b2b6b7a2c8c1441336838
```

The OCI layer digest was checked before extracting the header `.deb`. Its Debian
version is the original artifact hash, not the repository's reversioned
`26.11.0-trunk.108`; the kernel build/version is identical. Only headers and their
development dependencies were installed; the running kernel was not upgraded.
The header package and manifest were also saved off the SD card privately.

## Evidence and remaining tests

Selected logs and checksums are in [the UPS evidence directory](evidence/2026-10-27-ups/).
Full private backups of the previous boot environment, user panel settings,
deployment scripts and matching header package were saved off the SD card.

- Decoder ASan/UBSan tests passed on x86_64 and native AArch64: observed sample,
  identity mismatch, read errors, unstable multi-byte reads and invalid bounds.
- Host module build against Linux 7.0 headers passed; that x86 module was never
  copied to the board. Native DKMS module vermagic matches the running AArch64
  kernel. This external module sets the normal out-of-tree kernel taint.
- DT composition retained PWM1, enabled I2C1 and added `ups@10` with
  `compatible="dfrobot,dfr0528"` and `reg=0x10`.
- Real battery removal/error recovery, suspend/resume and future kernel upgrades
  remain untested; fake-read tests cover decoder errors only.
- Charger state needs a real hardware indication or independently qualified
  sensing method. Do not infer it from one voltage or percentage sample.
- Visible XFCE login, supply switchover under load and orderly shutdown before
  the firmware cutoff remain separate acceptance steps.
